# 目标文档

> 这份文档回答两个问题：**为什么做这个项目**，以及**做到什么程度算成功**。
>
> 它是四份文档的起点。技术选型见 [TECHNICAL.md](./TECHNICAL.md)，
> 具体设计取舍见 [DESIGN.md](./DESIGN.md)，不可逾越的红线见 [CONSTRAINTS.md](./CONSTRAINTS.md)。

---

## 一句话

从零构建一个**真正能用**的 Agent 骨架 —— 不是演示 ReAct 循环的玩具，
而是能承担真实任务、出问题时可以诊断、行为边界清楚的工程基座。

---

## 动机

这个项目同时服务两个目标，而且不分主次：

**1. 搞懂 Agent 的本质**

亲手实现每一个模块（工具、记忆、检索、子 agent、技能），而不是调用框架的现成能力。
判断「我懂了」的标准不是代码跑通，而是能回答：

- 这一行为什么这样设计？
- 不这样设计会付出什么代价？
- 换一个场景，这个设计还成立吗？

**2. 做出真能用的东西**

代码要在真实任务上跑得起来，而不是只在 demo 场景下成立。
「能用」的判据见下文，它不是感觉，是几条可以检验的标准。

这两个目标天然冲突：框架能省掉 80% 的代码，但也跳过了 80% 的理解。
本项目的取舍是 —— **宁可慢，也要自己实现；但实现标准按生产要求来。**

## 与 min-cursor 的关系

`min-cursor` 是另一个仓库（一个日常使用的 AI coding agent）。两者不是替代关系：

| | min-cursor | agent-harness |
|---|---|---|
| 定位 | 日常使用的 AI coding agent | 学习用的 Agent 骨架 |
| 优先级 | 能用就行，快速迭代 | 每一层都要能解释清楚 |
| 已覆盖模块 | tool、MCP、上下文管理 | 补齐 memory / rag / subagent / skill |
| 相互作用 | 踩过的坑 → 变成 harness 的设计依据 | 验证成熟的能力 → 回灌给 min-cursor |

**共享经验，不共享代码。** 一旦为了复用而把两个目的不同的东西搅在一起，
两边都会变得难以解释 —— 而那恰好是这个项目最不能接受的。

已经发生的第一次回灌：harness 在实现「命令输出捕获」时发现
`min-cursor` 用 `stdio: 'inherit'` 导致**模型看不到命令输出**，该问题已修复回 min-cursor。

## 模块范围

Agent 骨架由以下能力构成。每一条的要求都是「能用」，而不是「有」：

| 模块 | 要解决的本质问题 | 验收标准 | 状态 |
|---|---|---|---|
| **safety** | 让它敢被交出去自己跑 | 挂住的命令不拖死 Agent；越界路径被拒 | ✅ M0 |
| **tool** | Agent 与外部世界交互的接口 | 新增工具只改 1 个文件，且有测试覆盖 | ✅ M0（部分） |
| **agent** | 把「模型决策」和「工具执行」串成循环 | 能独立完成一个真实的小任务 | ⬜ M1 |
| **memory** | LLM 是无状态的，历史会丢 | 重启进程后仍记得上次沉淀的事实 | ⬜ M2 |
| **rag** | 模型不知道你的私有知识 | 提问能返回带来源、可追溯的答案 | ⬜ M3 |
| **subagent** | 主上下文的窗口是稀缺资源 | 子任务的中间过程不污染主上下文 | ⬜ M4 |
| **skill** | 重复的流程应该可复用 | 放一个文件就能被识别、选中、执行 | ⬜ M5 |
| **eval** | 「能用」必须可度量 | 有一组固定任务 + 可重复的通过率 | ⬜ M6 |

**两个补充说明：**

- **planning（任务规划）** 不在最初的模块清单里，但它是「demo」和「能用」的分水岭之一。
  纯 ReAct 靠模型每轮即时决策，长任务容易跑偏。它会在 M1 之后按需加入。
- **eval** 同样不在最初的清单里，但它是另一个分水岭：没有它，
  你无法判断一次改动是让 Agent 变好还是变坏，只能靠感觉。

## 非目标

明确**不做**的事。写下来是为了防止范围蔓延 —— 每一条都曾经是很有诱惑力的方向：

- **不做通用产品** —— 不追求支持所有模型、所有场景。先把一个场景做透。
- **不做框架** —— 不发布 npm 包、不考虑向后兼容、不为第三方 API 稳定性负责。
- **不做 UI** —— CLI 足够。可视化只服务于调试，不服务于产品化。
- **不重复造模型层** —— 用 OpenAI 兼容接口调现成模型，不做训练、不做微调。
- **不做容器级隔离** —— 进程沙箱超出范围（具体边界见 [CONSTRAINTS.md](./CONSTRAINTS.md)）。
  知道它的边界在哪，比假装它不存在要好。
- **不追求功能数量** —— 六个模块全部「有」但都不能用，不如三个模块真正能用。

## 成功判据

判断项目「做成了」的四条标志：

1. **能独立完成真实任务** —— 拿一个真实任务（例如「给某个项目加一个功能并跑通测试」）
   交给它，不需要人盯着逐步指挥。
2. **出错能自愈** —— 中途命令失败时，它能读到错误、换方案；
   而不是卡死、空转，或者谎报成功。
3. **行为在预期之内** —— 不会写到工作区外、不会无限重试、不会撑爆上下文。
   「不会做坏事」和「能做正事」同等重要。
4. **你能解释每一个设计** —— 每个模块在设计什么权衡。
   这一条无法自动化检验，但它是这个项目存在的理由。

## 里程碑

每个里程碑都以「可验证的能力」收尾，而不是以「写完了某个模块」收尾。

| 里程碑 | 内容 | 验收 |
|---|---|---|
| **M0** | 工程底座：超时、沙箱、测试基建 | ✅ 基础测试全绿；具备进程终止能力及失败反馈 |
| **M1** | LLM 接入 + ReAct 主循环 + 文件工具 | 能完成一个真实的小任务（如批量重命名 + 改代码） |
| **M2** | 会话内多轮 → 跨会话记忆 | 重启后仍记得上次沉淀的事实 |
| **M3** | 接入 RAG 检索 | 提问返回带来源的答案 |
| **M4** | 子 agent | 子任务中间过程不进入主上下文 |
| **M5** | 技能加载与选择 | 新增一个技能文件即可被使用 |
| **M6** | 任务集 + 通过率 | 同一批任务重复跑，通过率可比较 |

**为什么 M0 排在 M1 前面**：一个能跑的 ReAct 循环很好写，难的是让它敢被交出去自己跑。
先做完底座，后面每一层都站在稳的地基上；反过来先写循环，
后面补超时和沙箱时就得回头改一遍所有已经写好的工具。
