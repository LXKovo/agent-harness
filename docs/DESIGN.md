# 设计决策与待验证假设

> 本文解释取舍，不替代 [TECHNICAL.md](./TECHNICAL.md) 的实现说明或 [CONSTRAINTS.md](./CONSTRAINTS.md) 的边界。标为“拟议”的决定仍需 M1 实现和评测验证。

## D1 · 先完成工具底座（已实施）

**背景**：没有超时、路径检查和测试时，演示循环可以跑通，却难以判断它在真实任务中的失败原因。

**决定**：先实现工具注册表、命令和文件工具，再接模型。工具层已独立验证，现已接入首版单 Agent 循环；真实模型任务评测仍待完成。

**代价与边界**：前期缺少端到端体验；底座测试不能代替真实模型任务评测。“工程底座先做”也不表示路径检查已解决 shell 隔离。

## D2 · 命令超时必须检查终止结果（已实施，跨平台能力有限）

**背景**：`Promise.race` 能让调用方停止等待，却不会自行结束子进程。

**决定**：命令使用定时器；Windows 调用 `taskkill /t /f`，POSIX 对直接子进程发送 `SIGKILL`。终止失败返回具体错误，不报告成功。通用 `withTimeout()` 仍只负责等待超时，调用方不能把它当取消机制。

**代价与后续**：Windows 需要启动额外进程且可能被权限拒绝；POSIX 当前没有完整杀进程树。真实任务中的部分文件写入也不会因超时回滚。需要跨平台长跑时，应补进程组或隔离环境及对应验证。Node 的[子进程文档](https://nodejs.org/api/child_process.html#subprocesskillsignal)说明了经 shell 启动的后代进程问题。

## D3 · 结果回传模型，终端呈现另行实现（部分实施）

**背景**：`stdio: 'inherit'` 只把输出送到终端，工具调用者拿不到命令结果。

**决定**：`exec_command` 用 pipe 捕获 stdout、stderr、退出码及超时状态，结果以文本返回，输出过长时截断并继续消费管道。

**现状边界**：CLI 显示模型轮次和工具调用结束后的摘要，但没有命令输出实时透传。`getProcessor()` 的 `compact` 已被上下文压缩消费，`summarize` 仍没有消费者。

## D4 · 路径检查是局部防误操作机制（已实施）

**背景**：模型可能给文件工具提供 `../`、绝对路径或指向外部的链接。

**决定**：`resolveInWorkspace` 做词法检查；文件工具再解析真实目标或父目录，以阻止常见链接逃逸。写文件默认不覆盖已有文件。

**代价与边界**：真实路径检查存在检查与使用之间的竞态；shell 命令不受这些检查约束。当前代码没有进程级沙箱。需要执行不可信命令或无人值守运行时，先设计隔离或权限门禁。

## D5 · 工具定义和结果处理经注册表汇合（已实施）

**背景**：在 Agent 层按工具名写分支，会让新增工具时修改多处执行逻辑。

**决定**：工具提供 `name`、`description`、Zod `schema` 和 `invoke`；在 `src/tools/index.js` 注册，同时配置可选的 `compact` / `summarize` 处理器。路由层通过名称查找，不写工具专属分支。

**代价与边界**：新增工具仍需**工具文件、注册接线和测试**，不是“只改一个文件”。处理器目前在组装文件中；`compact` 已由上下文压缩消费，`summarize` 仍待消费。未来若增加动态工具，再评估是否让定义与处理器合并。

## D6 · 让模型得到错误，同时让运行时知道状态（现状有缺口）

**背景**：模型需要读到“文件不存在”“命令退出码非零”等结果，才能修正后续动作。另一方面，程序也需要可靠地区分工具成功、失败、截断和内部异常。

**现状**：`ToolRegistry.invoke()` 保留文本接口，供模型和现有调用方使用；`invokeResult()` 返回机器可读的状态、文本和截断标志。参数错误、未知工具与未捕获异常另有错误代码。内置工具在产生结果时明确标记状态，Agent 事件直接记录状态，不匹配中文文案。

**边界**：自定义的纯文本工具会被视为成功，若需要准确事件状态，应实现 `invokeResult()`。现有状态只描述一次工具调用的返回结果，不保证部分文件写入已回滚，也不保证超时后外部进程及其副作用已完全清理。

## D7 · 使用 Node 原生测试，评测从 Agent 首版开始（已实施 / 拟议）

**决定**：当前单元与工具测试使用 `node:test` 和 `node:assert`，不引入测试框架。M1 首版用假模型测试工具调用协议，并用独立临时工作区运行固定真实任务，由确定性文件检查器判定结果。

**进展与代价**：假模型和本地 HTTP 测试验证协议、循环及 CLI；七个文件任务、一个代码修复任务和一个沙箱任务会调用真实模型、检查最终工作区并保存 JSON 报告。最早四个任务的三轮基线为 12/12 通过，后五项只有小样本（24 模块探索 20 次答对 12 次，60 模块检索 5/5），样本仍很小，不能说明长期稳定性。评测方案应先小后大。参见 [OpenAI 的 Agent 指南](https://openai.com/business/guides-and-resources/a-practical-guide-to-building-ai-agents/)和 [Anthropic 的评测讨论](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)。

## D8 · 自研运行逻辑，以 Chat Completions 兼容接口起步（已实施，待实测）

**背景**：项目要理解工具选择与执行循环，不需要为了少依赖而自行实现每个模型协议细节。

**决定**：先用 `openai` SDK 调用可配置 `baseURL` 的 Chat Completions 兼容接口。Zod schema 在循环中转换为 JSON Schema；客户端负责请求与取消，循环负责工具调用 ID、预算、调度、停止条件和事件。每个目标模型仍须实测工具协议。

**边界**：不假定所有“OpenAI 兼容”服务都支持 Responses API、严格 schema 或相同的可选参数。只有真实服务出现明确差异时，才增加专门适配器；不预先建设多厂商框架。

## D9 · 单 Agent 结构化工具循环先行（首版已实施）

**决定**：首版由一个模型在轮数和总耗时预算内选择工具、读取结果并决定下一步。使用模型提供的结构化工具调用，不要求输出经典 ReAct 的 `Thought:` / `Action:` 文本。对于步骤固定的任务，可用普通程序工作流；对步骤未知的小型编码任务，工具反馈循环是合适起点。

**理由与代价**：单 Agent 更容易定位失败和建立基线；多 Agent、规划器、长期记忆及技能会增加调度和上下文成本。只有轨迹与评测显示明确瓶颈时再引入。此顺序与 [Anthropic 的简化架构建议](https://www.anthropic.com/engineering/building-effective-agents)及 [OpenAI 的单 Agent 迭代建议](https://openai.com/business/guides-and-resources/a-practical-guide-to-building-ai-agents/)一致。

## D10 · 上下文超预算先压缩，最后才终止（首版已实施）

**背景**：首版把 `AGENT_MAX_CONTEXT_CHARS` 当硬闸门 —— 一超预算就结束整次运行。读一个稍大的文件就可能让这一轮任务白跑，模型没有任何补救机会。

**决定**：预算分两级。达到硬预算的比例（默认 70%）先压缩历史，只有压缩后仍超硬预算才以 `context_limit` 终止。压缩分四级逐级加严：先用工具自己声明的 `compact` 处理器截断，不够再把上限收严，再不够把旧工具结果换成引用，最后丢弃整段早期历史。保护窗口（默认最近 2 次交换）不压缩。

**保护窗口（2026-10-19 修正）**：L1/L2 最初不区分保护窗口，窗口内刚产生的结果也会被截到 1200 字符 —— 24 模块夹具把关键字段放在文件末尾时因此永远读不到，模型还没看到就只剩开头。现在 L1–L4 都跳过窗口，只有窗口本身超过硬预算时才由 L5/L6 应急截断：截断只丢细节，终止丢掉整趟任务。`test/context.test.js` 补了两条回归用例（窗口内结果不被截断、刚读到的长结果在下一轮必须完整）。

**理由与代价**：压缩强度与上下文压力成正比，比一次性砍到很短更不容易丢掉模型正在用的细节。代价是：压缩只减少发往模型的文本，不回滚任何工具副作用，也不保证模型会重读被省略的文件；被丢掉的早期上下文无法恢复，模型只能靠重读文件或重跑命令重建。因此压缩事件必须可诊断（级别、省下字符、当前长度、阈值、估算 token），离线测试也必须验证「不拆散工具调用配对、幂等、压缩后仍超硬预算时正确终止」。

**为什么不用精确 token 预算**：字符预算不需要引入 tokenizer 依赖或联网，判定可复现；`context` 事件里的估算 token 只用于对照服务端口径的 `usage` 观察偏差量级。等真实轨迹显示字符口径明显失真时再换。

**顺序上的教训**：压缩必须排在硬闸门之前。第一版把硬预算检查放在前面，于是「恢复一个已经超预算的 checkpoint」会在第一次压缩之前就被终止 —— 压缩对最需要它的场景恰好无效。同级顺序和分级强度一样需要测试，这类问题只有把恢复路径也纳入用例才会暴露。

## D11 · 沙箱用一次性容器，且不允许静默降级（首版已实施）

**背景**：D4 已经说明路径检查只拦「走错路」，拦不住「恶意代码」。一旦让 Agent 自主执行命令，`cwd` 检查和环境变量过滤都不是隔离：命令仍能读工作区外的文件，也能读磁盘上的凭据。

**决定**：命令有两个互斥后端，由 CLI 显式选择。`--docker` 把命令放进一次性容器：只挂载工作区、根文件系统只读、无网络、丢掉全部 capability、禁止提权、限制内存与进程数，命令结束或超时后删除容器。拿不到 Docker 或镜像时**直接退出**，不退回进程内执行。`--allow-shell` 保留给可信目录，并在文档里继续标注为无隔离。

**代价与边界**：容器共享宿主内核，不是虚拟机；容器逃逸类漏洞仍可能突破。容器内默认以 root 运行，它写出的文件在宿主机上的属主可能与预期不同。每次执行都要起一个容器，单条命令的开销从毫秒级升到秒级 —— 真实测评里一条 `node --test` 约 0.6 秒，可以接受，但高频小命令会明显变慢。镜像由使用者负责拉取与信任，本仓库不校验镜像内容。

**为什么拒绝降级**：安全开关最容易出的错不是「读不到 Docker 报错」，而是「以为有隔离、其实在裸跑」。所以不可用时宁可拒绝执行，把选择权交回使用者。

## D12 · 同轮工具调用并发，但按路径串行（首版已实施）

**背景**：真实轨迹里 10 轮有 7 轮，模型在同一轮里发出 2–3 个互不相关的调用（各读一个文件、各搜一次）。原先逐条 await，把这些本来就独立的等待叠了起来；沙箱模式下每条命令还有 0.5–1 秒容器开销，串行更贵。

**决定**：同轮调用并发执行，但保留三条确定性保证。第一，并发只负责「执行」；追加 tool 消息、写 checkpoint、发事件统一按模型给出的调用顺序做，和串行版本完全一致。第二，同一路径的调用串行 —— 按 `filePath`、`cwd` 或 `path` 维护一条串行链，后一条先 await 前一条完成。第三，checkpoint 粒度仍是「一条调用」：每条各自写 `tool_running` 与 `tool_batch`，所以崩溃恢复时只有正在飞的那一条会被标为「结果未知」。

**为什么必须按路径串行**：两个 `apply_patch` 改同一个文件时，如果都读到旧内容再各自原子替换，后写的那次会静默覆盖前一次 —— 文件内容看起来正常，但其中一次修改消失了。这不是理论风险，而是并发写文件的常规失败方式。

**为什么 checkpoint 写入要「入队并等待」而不只是入队**：并发执行时，调用 A 的结果写入与调用 B 的开始写入会排在同一条队列里。如果 A 只是入队就继续，B 的开始快照可能先落库，而 A 那条带结果的写入一旦失败，A 的结果就再也没落盘。结果已经算出来、只是没写成功，属于不该出现的丢数据。

**踩过的坑**：并发只做「执行」，不要顺手做「追加」。第一版让每个并发分支各自追加消息、各自发事件，于是消息顺序变成完成顺序（快的先追加），checkpoint 顺序也随之漂移。测试直接抓到了这一点。另外，用「阶段划分」表达串行规则时，后建立的阶段会整体等待前一个阶段结束，从而顺带卡住无关的调用；实际执行改用按路径的串行链，`planPhases()` 保留为规则的显式说明与测试基准。

## D13 · 重试只放在模型层（首版已实施）

**背景**：一次网络抖动或一次 429，会让整次任务以 `model_error` 结束。之前 SDK 的 `maxRetries` 被显式设为 0。

**决定**：模型请求按 `AGENT_MODEL_MAX_RETRIES`（默认 2）重试，交给 `openai` SDK 做指数退避并尊重 `Retry-After`。工具层不自动重试。

**为什么工具不能自动重试**：`write_file`、`apply_patch`、`exec_command` 都有副作用，自动重试等于重复执行；而模型请求幂等，重发一次没有额外后果。这条边界与 D6 同一思路：让运行时知道状态，并只在能证明安全的地方自动恢复。

**代价**：重试会消耗总耗时预算（`AGENT_MAX_DURATION_MS`），两者必须一起看。重试耗尽后的错误会带上状态码与重试次数，便于区分「服务端故障」与「配置错误」。

## D14 · 子 Agent 与规划器暂缓，先建立能证明瓶颈的评测（拟议）

**背景**：GOALS 把子 Agent 列为候选扩展，理由是单 Agent 在上下文容量和并行度上有理论上限。但已跑过真实模型的七个固定任务全部通过，记录到的过程失败只有两类：参数写错后自我纠正、先跑失败测试再修代码。没有一条失败来自「上下文装不下」或「需要并行隔离」——唯一的上下文压力是人为把预算压到 20000 才触发的单次样本。

**决定**：M1 不引入子 Agent、规划器或多层调度。准入需要同时满足三条：① 有一个「大面积探索」式固定任务（例如 50+ 文件里定位一处配置，单次探索会越过上下文硬预算）；② 该任务上单 Agent 连续多轮稳定失败，且失败可归因于上下文或隔离需求，而不是参数错误、模型误判或夹具缺陷；③ 先定义清楚预算继承、权限继承、checkpoint 语义、取消传递、结果回传压缩这五件事。

**理由与代价**：在本仓库里子 Agent 只能是一个 `spawn_agent` 工具，在 `runAgent()` 里递归调用自己。它引入的不是一个文件，而是五处跨模块决定，每一处都要能说清解决的具体失败模式；没有这个失败模式，提前做就只剩「演示复杂度」。代价是暂时放弃「大仓库一次性探索」，也不要把它当成默认策略——当前的替代手段是同轮并发（D12）加 `search_files` 的定向检索。

**当前进展**：准入实验的夹具已落地，即 `explore-large-repo`——60 个服务模块合计约 150KB，超过 120000 字符默认硬预算，逐个通读必然触发压缩；目标常量 `EU_WEST_3_ENDPOINT` 全库唯一，另有 8 个同形诱饵，宽泛搜索命中 9 处、精确搜索命中 1 处。离线测试只验证了夹具形状（文件数、总体积、常量唯一性），**尚未用真实模型跑过**。

另加了互补的 `sweep-audit-weights`：24 个约 5.5KB 的模块合计约 134KB，每个模块首行审计记录里的 `weight` 位于第 322 列（`search_files` 每行只回显前 300 字符），所以只能逐个读取。累计 20 次真实运行（修复保护窗口前后各 10 次）**12 次答对**，8 次失败全部来自预算（5 次 16 轮、3 次 120 秒），**没有一次 `context_limit`**；多轮用「命中/未命中」逐位试探绕开了通读。`explore-large-repo` 修复后跑出 **5/5**，每轮 3 次调用、约 3 秒 —— 它测的是检索路径，本来就不构成上下文压力。结论是单 Agent 能完成这类探索，瓶颈是时间和轮数，不是上下文容量或并行隔离 —— 本节的准入条件仍未满足。下一步不是 `spawn_agent`，而是确定这类任务的耗时/轮数预算，以及是否要让「逐位试探」不再比读取划算。

**相关缺口**：`getProcessor().summarize` 至今没有消费者（见 D3），而「子 Agent 只回摘要、不回完整轨迹」正是它最自然的消费者。将来真要引入子 Agent，回传压缩应与它一起设计，而不是再新增一套截断逻辑。

## 需要在 M1 明确的决定


| 问题 | 做决定所需证据 |
|---|---|
| 目标兼容服务是否可直接使用现有客户端 | 真实服务的工具调用、取消、错误和用量信息能否可靠取得 |
| 工具成功状态如何表示 | 假模型与真实模型轨迹能否清晰区分失败、截断和协议错误 |
| shell 权限与隔离策略 | 目标任务是否必须自主执行命令；运行环境是否可信 |
| 上下文预算及压缩 | 固定任务的实际 token 增长与失败轨迹（首版已实现分级压缩，待真实轨迹验证） |
| 后续是否需要规划、检索或子 Agent | 已定：暂缓，等有任务能证明单 Agent 稳定失败，见 D14 |

## 历史经验来源

`min-cursor` 的命令输出未回传模型、按工具名在多处写分支等经历，促成了本仓库的 D3 与 D5。这些是设计动机，不代表本仓库已实现完整 Agent；两个仓库也不互相 import 代码。
