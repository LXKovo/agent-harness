# 设计文档

> 这份文档记录**关键设计决策与取舍**。
>
> 每一条都包含：背景、决策、理由、被否决的方案、代价。
> 写下「被否决的方案」和「代价」是刻意的 —— 只知道「我们这么做」，
> 而不记得「为什么不那么做」，下次遇到同样的岔路口还是会犹豫。
>
> 硬性规则见 [CONSTRAINTS.md](./CONSTRAINTS.md)，本文档保留讨论余地。

## D1 · 工程底座先于 Agent 循环

**背景**
项目从零开始。最自然的起手是「先把 ReAct 循环跑起来，能对话了再加别的」，
因为这样最快看到成果。

**决策**
先做 safety（沙箱、超时）、tools（注册表、命令执行）和测试基建，**暂不做 Agent 循环**。

**理由**
一个能跑的 ReAct 循环大约 100 行，一天就能写完。难的是让它敢被交出去自己跑：

- 没有超时，一条挂住的命令让整个 Agent 永久等待
- 没有路径校验，模型生成的一个 `../` 就写到工作区外
- 没有测试，上面两条改一次就可能悄悄失效

这些是**地基**。反过来先写循环，等补底座时就得回头改一遍所有已写好的工具。

**被否决的方案**
「先跑起来再说」—— 它的问题不是顺序错了，而是**验证不了**：
循环跑通了不代表底座是对的，而底座错了会在后面每一层以奇怪的形式暴露出来。

**代价**
前几轮看不到「Agent」的样子，只有工具和工具测试。
对一个以「看到成果」为动力的项目来说，这是真实的心理成本。

## D2 · 超时 ≠ 停止等待

**背景**
`Promise.race([work, timeout])` 是最常见的超时写法，几行就能写完。

**决策**
不用 `Promise.race` 处理子进程。改用 `setTimeout` + `killTree`：

- Windows：`taskkill /pid <pid> /t /f`（`/t` 杀整棵进程树）
- POSIX：`child.kill('SIGKILL')`

**理由**
`Promise.race` 只做到「我这边不再等」，**子进程依然在后台运行**。

具体到 Agent 场景：`pnpm install` 起了 node，node 又起了自己的子进程。
只杀 shell 不杀树，结果是「Agent 看起来没卡住，机器上却留着几个占着端口和 CPU 的僵尸命令」。
这种问题在开发时几乎不会暴露，在长跑时才会。

**被否决的方案**
- 只用 `Promise.race` —— 表面能用，实际没解决问题
- 用 `child.kill()` 而不带 `/t` —— 在 Windows 上只终止 shell 本身

**代价**
Windows 上要多起一个 `taskkill` 子进程；跨平台两条分支要各自维护和验证。
因此这一条专门配了验证脚本（见 [TECHNICAL.md](./TECHNICAL.md) § 6），
因为单元测试只能断言「迅速返回」，断言不了「进程已死」。

## D3 · 命令输出必须回传模型

**背景**
`min-cursor`（另一个仓库）用 `stdio: 'inherit'` 执行命令：输出直接打到终端，
工具的返回值里**没有输出内容**。

于是模型执行完 `ls`、`git status`、`pnpm test` 之后拿不到任何结果 ——
它只能假设成功。这对 coding agent 是硬伤。

**决策**
用 `stdio: ['ignore', 'pipe', 'pipe']` 捕获 stdout / stderr，随工具结果返回给模型；
**同时**把捕获到的内容原样转发给终端（`logger.commandOutput`），实时可见的体验不变。

**理由**
Agent 的输出有两个消费者，需求不同：

| 消费者 | 需要什么 | 处理方式 |
|---|---|---|
| 模型 | 有界、结构化的结果 | 累积 + 按上限截断 |
| 人（终端） | 完整、实时的进度 | 原样透传，不截断 |

两者必须**同时**满足，少一个都会出问题：只给模型，人看不到进度、以为卡死；
只给人，模型就是在瞎猜。

**被否决的方案**
保持 `inherit` —— 代码更简单，但等于让 Agent 失去「读结果」的能力。

**代价**
- 截断逻辑要自己维护，而且比看上去容易写错：
  管道会攒一大块再一次性投递，**单个 chunk 就可能超过上限**，
  所以必须真的切片，光判断「累积前是否已满」不够。
  这个 bug 在本项目的第一次测试运行中就被抓出来了。
- 必须继续消费输出（即使已经截断），否则管道写满会把子进程卡死。

## D4 · 沙箱只管路径，并明确说出来

**背景**
怎么防止 Agent 写到工作区外？直觉答案自然是「做个沙箱」。

**决策**
`src/safety/sandbox.js` 只做一件事：**校验路径是否落在工作区内**。
并在代码注释、README 和 [CONSTRAINTS.md](./CONSTRAINTS.md) 中**显式声明它拦不住什么**。

**理由**
安全的敌人不是「做得少」，而是「以为做够了」。

一个只校验路径的模块如果被叫做「沙箱」而不加说明，
使用者会默认它对命令执行也有效 —— 而 `exec_command` 走 shell，
完全绕过路径校验。这种**错误的安心**比没有防护更危险。

**被否决的方案**
- 假装它是完整沙箱 —— 短期省事，长期埋雷
- 直接上容器（Docker / Firejail）—— 隔离强度够，但引入使用门槛
  （目标机器要有 Docker、要拉镜像、要处理挂载），超出本项目范围

**代价**
安全性依赖**上游正确理解这个边界**。这一点只能靠文档和注释反复说清，
无法靠代码强制。对于铁了心要越权的代码，这一层无能为力。

## D5 · 结果处理走注册表，不写 `if (toolName === ...)`

**背景**
工具结果有两个消费方向：给模型的（可能需要截断）和给终端的（一行摘要）。
`min-cursor` 的做法是在两个不同文件里各写一遍 `if (toolName === 'xxx')`，
结果是新增一个工具要改 3 处，而 MCP 动态加载的工具只能走通用兜底。

**决策**
工具在注册时**自带**它的 `compact` 和 `summarize` 处理器：

```js
registry.register(createExecCommandTool(settings), {
  summarize: (result) => result.split('\n')[0],
  compact: (result) => result,
});
```

路由层只做一次查找：`getProcessor(name) ?? GENERIC_PROCESSOR`。

**理由**
把「这个工具的输出该怎么处理」放在**工具自己的定义旁边**，
而不是散落在消费端。加多少工具都不用碰路由代码。

**被否决的方案**
- 继续用 `if` 分支 —— 已在 min-cursor 上验证过代价
- 把所有处理器集中到一个大文件 —— 改动了耦合位置，但没减少改动点数量

**代价**
- 工具定义处多了一个可选参数，简单工具也得想一下「有没有专属处理器」
- 处理器与工具在同一个文件里，文件的职责变得稍宽

## D6 · 工具永不抛错

**背景**
工具执行失败时，最自然的做法是 `throw` / `reject`，让调用方处理。

**决策**
工具**从不抛错**。所有异常（找不到工具、参数校验失败、执行异常）
都转成可读字符串返回。`registry.invoke` 的返回类型**永远是 `string`**。

**理由**
这是 ReAct 能工作的前提。Agent 循环的每一步都是：
「模型决定 → 工具执行 → **结果回到模型** → 模型决定下一步」。

如果工具抛错，错误就绕过了模型直接打断循环 —— 而「看到错误、换一条路」正是
ReAct 相对脚本化自动化的核心优势。让模型看到 `退出码 127: command not found`，
它有机会换成正确的命令；让它收到一个异常，整个任务就结束了。

**被否决的方案**
抛错让上层统一处理 —— 会在 Agent 层堆一层 try/catch，
而且丢失了「错误是给模型看的信息」这个语义。

**代价**
**真正的代码 bug 可能被当成「工具失败」吞掉。**
缓解方式是在错误文本中保留足够信息（`工具 "x" 执行出错: <原始 message>`），
并且工具自身的逻辑要有测试覆盖 —— 不能指望 Agent 帮你发现 bug。

## D7 · 用 `node:test` 而不是 vitest / jest

**背景**
测试基建要选框架。vitest 生态成熟、DX 好；jest 更老牌；Node 有内置的 `node:test`。

**决策**
用 Node 内置的 `node:test` + `node:assert`，**不引入任何测试框架**。

**理由**
1. **零依赖** —— Node 20+ 自带，`node --test` 直接跑，不需要配置、不需要转换、没有插件链
2. **符合项目气质** —— 这个项目的目的是理解每一层。每引入一个框架就多一层黑盒，
   而测试恰恰是最不该有黑盒的地方：你要能说清一个断言是怎么被执行的
3. Node 24 的 test runner 已足够成熟：支持 `describe`/`test`、`--watch`、并发

**被否决的方案**
vitest —— DX 确实更好（更好的快照、mock、报告），但为此要引入
一整套依赖树和配置，收益与本项目的目的不匹配。

**代价**
- 没有内置的 mock 生态与快照测试（需要时得自己写替身）
- 报告输出不如 vitest 美观
- 如果将来要做覆盖率报告，需要额外接入

## D8 · 工具层不依赖 LangChain

**背景**
`min-cursor` 用 `@langchain/core` 的 `tool()` 定义工具，由 LangChain 负责
把 Zod schema 转成 JSON Schema 并绑定到模型。

**决策**
自定义一个极简契约，不引入 LangChain：

```js
{ name, description, schema /* zod */, invoke(args) → string }
```

**理由**
`tool()` 提供的核心价值只有两件事：schema 转换、与模型的绑定。
这两件都能自己写（zod v4 自带 `z.toJSONSchema()`），
而自己写的收益是**能看清工具调用的全过程** —— 从「模型返回一个 tool_call」
到「参数被校验」到「结果变回一条消息」，每一步都在自己的代码里。

**被否决的方案**
直接复用 LangChain —— 更省事，但会把最难理解的那一层（模型与工具的协议）变成黑盒。

**代价**
- M1 接入模型时要自己写 schema → JSON Schema 的转换与 `tool_calls` 的解析
- 失去 LangChain 生态的现成集成（流式、回调、多 provider 适配）
- 如果之后要支持多个模型 provider，这部分适配成本要自己承担

**注意**：这条只约束**工具层**。M1 选择模型接入方式时，
是否用 LangChain 的模型封装（`@langchain/openai`）是另一个独立决策，见下文。
