# 设计决策与待验证假设

> 本文解释取舍，不替代 [TECHNICAL.md](./TECHNICAL.md) 的实现说明或 [CONSTRAINTS.md](./CONSTRAINTS.md) 的边界。标为“拟议”的决定仍需 M1 实现和评测验证。

## D1 · 先完成工具底座（已实施）

**背景**：没有超时、路径检查和测试时，演示循环可以跑通，却难以判断它在真实任务中的失败原因。

**决定**：先实现工具注册表、命令和文件工具，再接模型。工具层已独立验证，现已接入首版单 Agent 循环；真实模型任务评测仍待完成。

**代价与边界**：前期缺少端到端体验；底座测试不能代替真实模型任务评测。“工程底座先做”也不表示路径检查已解决 shell 隔离。

## D2 · 命令超时必须检查终止结果（已实施，跨平台能力有限）

**背景**：`Promise.race` 能让调用方停止等待，却不会自行结束子进程。

**决定**：命令使用定时器；Windows 调用 `taskkill /t /f`，POSIX 对直接子进程发送 `SIGKILL`。终止失败返回具体错误，不报告成功。通用 `withTimeout()` 仍只负责等待超时，调用方不能把它当取消机制。

**代价与后续**：Windows 需要启动额外进程且可能被权限拒绝；POSIX 当前没有完整杀进程树。真实任务中的部分文件写入也不会因超时回滚。需要跨平台长跑时，应补进程组或隔离环境及对应验证。Node 的[子进程文档](https://nodejs.org/api/child_process.html#subprocesskillsignal)说明了经 shell 启动的后代进程问题。

## D3 · 结果回传模型，终端呈现另行实现（部分实施）

**背景**：`stdio: 'inherit'` 只把输出送到终端，工具调用者拿不到命令结果。

**决定**：`exec_command` 用 pipe 捕获 stdout、stderr、退出码及超时状态，结果以文本返回，输出过长时截断并继续消费管道。

**现状边界**：CLI 显示模型轮次和工具调用结束后的摘要，但没有命令输出实时透传。`getProcessor()` 虽能取得摘要和压缩函数，目前没有运行时消费它们。

## D4 · 路径检查是局部防误操作机制（已实施）

**背景**：模型可能给文件工具提供 `../`、绝对路径或指向外部的链接。

**决定**：`resolveInWorkspace` 做词法检查；文件工具再解析真实目标或父目录，以阻止常见链接逃逸。写文件默认不覆盖已有文件。

**代价与边界**：真实路径检查存在检查与使用之间的竞态；shell 命令不受这些检查约束。当前代码没有进程级沙箱。需要执行不可信命令或无人值守运行时，先设计隔离或权限门禁。

## D5 · 工具定义和结果处理经注册表汇合（已实施）

**背景**：在 Agent 层按工具名写分支，会让新增工具时修改多处执行逻辑。

**决定**：工具提供 `name`、`description`、Zod `schema` 和 `invoke`；在 `src/tools/index.js` 注册，同时配置可选的 `compact` / `summarize` 处理器。路由层通过名称查找，不写工具专属分支。

**代价与边界**：新增工具仍需**工具文件、注册接线和测试**，不是“只改一个文件”。处理器目前在组装文件中，且尚未有消费者；未来若增加动态工具，再评估是否让定义与处理器合并。

## D6 · 让模型得到错误，同时让运行时知道状态（现状有缺口）

**背景**：模型需要读到“文件不存在”“命令退出码非零”等结果，才能修正后续动作。另一方面，程序也需要可靠地区分工具成功、失败、截断和内部异常。

**现状**：`ToolRegistry.invoke()` 总返回字符串，把参数错误和异常文本化。这支持模型继续处理，但上层若只匹配字符串，就会受文案变化影响；开发错误也可能被当作普通工具失败。

**M1 进展与缺口**：现已记录模型轮次、工具名、调用 ID、耗时及部分协议错误类别；`registry.invoke()` 仍返回文本，工具内部 I/O 失败没有统一的机器可读状态。事件中的 `returned` 只表示工具返回内容。下一步应补全成功、失败和截断状态，不靠匹配中文文案判断。

## D7 · 使用 Node 原生测试，评测从 Agent 首版开始（已实施 / 拟议）

**决定**：当前单元与工具测试使用 `node:test` 和 `node:assert`，不引入测试框架。M1 首版用假模型测试工具调用协议，并用独立临时工作区运行固定真实任务，由确定性文件检查器判定结果。

**进展与代价**：假模型和本地 HTTP 测试验证协议、循环及 CLI；三个文件任务和一个 shell 代码任务会调用真实模型、检查最终工作区并保存 JSON 报告。当前四个任务的 3 轮基线为 12/12 通过，但样本仍很小，不能说明长期稳定性。评测方案应先小后大。参见 [OpenAI 的 Agent 指南](https://openai.com/business/guides-and-resources/a-practical-guide-to-building-ai-agents/)和 [Anthropic 的评测讨论](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)。

## D8 · 自研运行逻辑，以 Chat Completions 兼容接口起步（已实施，待实测）

**背景**：项目要理解工具选择与执行循环，不需要为了少依赖而自行实现每个模型协议细节。

**决定**：先用 `openai` SDK 调用可配置 `baseURL` 的 Chat Completions 兼容接口。Zod schema 在循环中转换为 JSON Schema；客户端负责请求与取消，循环负责工具调用 ID、预算、调度、停止条件和事件。每个目标模型仍须实测工具协议。

**边界**：不假定所有“OpenAI 兼容”服务都支持 Responses API、严格 schema 或相同的可选参数。只有真实服务出现明确差异时，才增加专门适配器；不预先建设多厂商框架。

## D9 · 单 Agent 结构化工具循环先行（首版已实施）

**决定**：首版由一个模型在轮数和总耗时预算内选择工具、读取结果并决定下一步。使用模型提供的结构化工具调用，不要求输出经典 ReAct 的 `Thought:` / `Action:` 文本。对于步骤固定的任务，可用普通程序工作流；对步骤未知的小型编码任务，工具反馈循环是合适起点。

**理由与代价**：单 Agent 更容易定位失败和建立基线；多 Agent、规划器、长期记忆及技能会增加调度和上下文成本。只有轨迹与评测显示明确瓶颈时再引入。此顺序与 [Anthropic 的简化架构建议](https://www.anthropic.com/engineering/building-effective-agents)及 [OpenAI 的单 Agent 迭代建议](https://openai.com/business/guides-and-resources/a-practical-guide-to-building-ai-agents/)一致。

## 需要在 M1 明确的决定

| 问题 | 做决定所需证据 |
|---|---|
| 目标兼容服务是否可直接使用现有客户端 | 真实服务的工具调用、取消、错误和用量信息能否可靠取得 |
| 工具成功状态如何表示 | 假模型与真实模型轨迹能否清晰区分失败、截断和协议错误 |
| shell 权限与隔离策略 | 目标任务是否必须自主执行命令；运行环境是否可信 |
| 上下文预算及压缩 | 固定任务的实际 token 增长与失败轨迹 |
| 后续是否需要规划、检索或子 Agent | 单 Agent 基线在哪些任务上稳定失败 |

## 历史经验来源

`min-cursor` 的命令输出未回传模型、按工具名在多处写分支等经历，促成了本仓库的 D3 与 D5。这些是设计动机，不代表本仓库已实现完整 Agent；两个仓库也不互相 import 代码。
