# 约束文档

> 这份文档记录**不可逾越的规则**。
>
> 与 [DESIGN.md](./DESIGN.md) 的区别：设计文档解释「为什么这样做」，可以有讨论余地；
> 约束文档是硬性的 —— 违反它必须停下来修，而不是记一笔「下不为例」。

---

## 一、安全红线

### 1.1 凭据绝不入库

- 任何 API Key、Token、密码**只放在 `.env`**，`.env` 必须在 `.gitignore` 中
- 配置文件中的密钥引用一律用 `${ENV_VAR}` 占位符，不写明文
- **公开仓库推送前必须扫描一次**：

```powershell
Get-ChildItem -Recurse -File | Where-Object {
  $_.FullName -notmatch 'node_modules|\.git\\'
} | Select-String -Pattern 'gho_|ghp_|sk-[A-Za-z0-9]{20}|PRIVATE KEY|Bearer [A-Za-z0-9_-]{20}'
```

命中任何一条，**中止推送**并先处理。

### 1.2 不把本机路径写死

`D:\Git\Git\bin\bash.exe` 这类路径只能作为**探测候选之一**，不能作为唯一默认值。
原因很直接：换一台机器就失效，而失效方式是「命令静默跑到别的 shell 里」，
不是报错 —— 这种 bug 最难查。

### 1.3 危险操作要有边界

任何会修改外部状态的工具（写文件、执行命令、调远端 API）必须至少满足：

- 有明确的**范围限制**（如工作区路径边界）
- 有**失败路径**（出错返回文本，不抛异常）
- 有**资源上限**（超时、输出长度）

## 二、能力边界（不许含糊）

写清「做不到什么」，比宣称「安全」更重要。以下边界必须在代码注释和文档中如实声明：

### 2.1 沙箱只管路径，不管进程

`src/safety/sandbox.js` 能拦住：

- ✅ `../` 逃逸
- ✅ 工作区外的绝对路径
- ✅ 空路径、非绝对路径的 root

它**拦不住**：

- ❌ `exec_command` 执行的命令 —— 走 shell，可在系统任意位置读写
- ❌ 工作区内指向外部的符号链接（`resolve` 不做真实路径解析）
- ❌ 恶意代码本身

**真正的进程级隔离需要容器**（Docker / Firejail / Windows Sandbox），不在本项目范围内。
因此上游调用方必须知道：这一层是**防模型走错路**，不是防攻击。

### 2.2 超时保证的是「不阻塞」，不是「一定干净」

`killTree` 已能终止 Windows 上的整棵进程树（`taskkill /t /f`）和 POSIX 上的子进程（`SIGKILL`）。
但它不保证：

- 子进程已经自行清理的临时文件被删除
- 子进程写入磁盘的部分结果被回滚
- 极端情况下操作系统拒绝终止进程

即：**超时能保证 Agent 继续往下走，不保证外部状态没有半成品。**

### 2.3 输出截断是有损的

命令输出超过 `MAX_OUTPUT_CHARS` 后会被截断，模型看到的是不完整的结果。
如果某个任务依赖完整输出（例如需要解析全部日志），必须显式调大上限，
而不是假设模型能拿到全部内容。

## 三、代码约定

### 3.1 语言与风格

- **ESM**：`import` / `export`，不用 `require`
- **缩进 4 空格**（与 `src/` 现有代码一致）
- 命名：模块与函数 `camelCase`，类 `PascalCase`
- 注释用中文，解释**为什么**而不是**是什么**

### 3.2 工具必须遵守的四条

工具的定位是「给模型用的函数」，不是普通函数：

1. **永不抛错** —— 所有异常 catch 后转成可读字符串返回。
   模型需要看到失败原因，抛错会直接打断 ReAct 循环。
2. **纯函数** —— 不写日志、不做终端输出。所有呈现由上层（logger / registry）负责。
3. **返回字符串** —— 返回结构化对象会让模型难以理解。
4. **`description` 面向模型写** —— 它决定模型什么时候调用这个工具，不是给人看的文档。

### 3.3 结果处理走注册表，不许写 `if (toolName === ...)`

新增工具时，它的 `compact` / `summarize` 处理器随工具一起注册到
`src/tools/registry.js`。**禁止**在路由层、Agent 层或任何其他地方
用工具名做分支判断 —— 这是 min-cursor 里已经付出过代价的教训。

### 3.4 新增工具必须同时新增测试

没有测试的工具视为未完成。测试至少要覆盖：

- 正常路径
- 失败路径（非 0 退出码 / 文件不存在 / 参数不合法）
- 上限行为（超时、截断、越界）

## 四、依赖与测试约束

### 4.1 依赖最小化

当前依赖只有 `zod` 一个，这是刻意的。

- 引入新依赖前先问：**自己写要多少行？**
  如果答案是「十几行」，就自己写 —— 这个项目的目的之一就是理解每一层。
- **不引入测试框架**。用 Node 内置的 `node:test`，理由见 [DESIGN.md](./DESIGN.md)。

### 4.2 测试必须离线可跑

`pnpm test` 不得依赖网络、外部服务、真实 API Key。
需要外部资源时，用注入依赖或本地假实现，不要 mock 到失去意义。

### 4.3 测试必须稳定

- 涉及时间的用例，用「相对耗时」断言（例如「远小于 30 秒」），不要断言精确毫秒数
- 涉及进程的用例，必须自行清理产生的进程与文件
- 任何偶发失败的测试都要修，不允许「重跑一次就过」——那等于没有测试

## 五、资源预算

这些数字是上限，不是建议值：

| 项 | 默认上限 | 环境变量 | 为什么 |
|---|---|---|---|
| 单条命令超时 | 30 秒 | `COMMAND_TIMEOUT` | 交互式任务的合理等待上限 |
| 模型可指定的超时 | 10 分钟 | `MAX_COMMAND_TIMEOUT` | **必须封顶**，否则模型能自己把超时保护关掉 |
| 单条命令返回给模型的输出 | 8000 字符 | `MAX_OUTPUT_CHARS` | 一次 `pnpm install` 的日志能吃掉大半个上下文窗口 |

**关于上限的一条原则**：凡是「模型可以自己指定」的资源参数，都必须有服务端封顶。
模型给自己开无限超时、无限输出，是把保护机制变成摆设的常见方式。

## 六、违反约束怎么办

1. **停下来**，不要在违规的基础上继续叠加功能
2. 判断是哪一类问题：
   - 安全红线 → 立即修复，并检查是否已经泄露（尤其是已推送的公开仓）
   - 能力边界被误述 → 修正文档和注释，让边界重新可见
   - 代码约定 → 修复后再提交
3. 如果约束本身不合理（确实太严或与现实冲突），**改这份文档**，
   而不是在代码里偷偷绕过去。约束的价值在于它被写下来且被遵守。
